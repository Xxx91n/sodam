# 诊断日志落在数据目录、默认开启，且与「清空缓存」分离

发布版是没有控制台的，全仓库的诊断输出都被丢弃，用户报障时维护者手上什么都没有。我们决定给
SodaM 加一个默认开启的本机日志出口，规则如下。

**位置在用户数据目录，不在缓存目录。** Linux 走 `XDG_STATE_HOME`（规范原文把 logs 归 state），
Windows 走 `%LOCALAPPDATA%\sodam\logs`，macOS 走 `~/Library/Application Support/sodam/logs`。
两个理由：缓存目录会被系统清理工具和自家的「清空缓存」一起扫掉；XDG 与主流桌面应用（VS Code、
PowerToys、OBS）都把日志视为应用数据而非可再生缓存。

**「清空缓存」不删日志，另设「清除诊断日志」。** 日志的价值就是出事之后还在，而用户点「清空缓存」
的动机常常正是修播放问题——顺手删掉证据会让排障当场断裂。磁盘压力由轮转上限解决：单文件 5 MB、
保留 5 份、合计约 30 MB。

**默认开，`INFO` 级。** 用户不会去配环境变量，默认关等于没有。为此环境变量的语义从「写不写」
改为「写到多细」，并且不提供「完全关闭日志」的选项，至少错误级不可关。

**只记到「播放尝试」，不假装能数请求。** 一次播放尝试内部要发几次远程请求，取决于 libresoda 的
内部实现（取下载信息、取音频体，失败时还会回退到缓存信息），本仓库看不到。所以日志记到尝试这一层：
每次尝试一行开始、每次失败一行带阶段与判定、放弃时一行带原因。要数到请求级，需要在 libresoda
提供钩子，属于另一个仓库的事。

**不引日志依赖。** `tracing-appender` 至今没有按大小轮转（tokio-rs/tracing#1940 开了三年），
最后还是得自己写；时间戳与轮转各几十行，不值得为它拉一条依赖链。

## Status

accepted

## Considered Options

- **日志跟 `audio/`、`covers/` 一起放缓存根，`clear_cache` 一并删**：被否。见上，会把排障证据
  和临时文件同等对待；issue 原判据写的就是这个，已在 issue 上改写。
- **默认关，靠环境变量或设置项开启**：被否。判据要求「断网后重启仍能看到」，默认关就做不到；
  Firefox 是这么做的，但它的用户群与排障流程不同。
- **接 `log` + `tracing-appender`**：被否。理由同上，且与「领域层不依赖多余基础设施」的约定相悖。
- **硬编码「每次尝试 2 个远程请求」**：被否。这个数字随上游重试路径变化，写死即成假数据。

## Consequences

- 日志目录与缓存目录是两个根，清理逻辑、空间统计、隐私说明都要分别写。
- 默认开启意味着隐私文档必须同步：`PRIVACY.md` 第 5 节原来说「只有开启环境变量才输出到终端」，
  已改写为「默认写在本机文件、写什么、不含什么」。
- 日志里保留接口地址（查询串已切断），因此日志文件本身不宜公开上传；设置页需要给出这个提醒。
